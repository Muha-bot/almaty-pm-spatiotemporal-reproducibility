This maps every figure caption found in the manuscript against what this
repository actually contains, so nobody assumes `figures/` is a 1:1 mirror
of the paper's figure list. It is not, and that is expected for a
reproducibility package — most packages ship extra diagnostic plots and do
not always regenerate every published panel. What matters is that the gap
is documented rather than silently discovered by a reviewer.

## Figure 6: recovered archive (2026-09-22), plus a separate non-matching reconstruction

**What matches the manuscript.** `data/archived/same_sensor_representativeness_v1/`
was recovered from the earliest reproducibility package supplied for this
manuscript (`Almaty_PM25_advanced_validation.zip`), which had not
previously been copied into this repository — the same recovery situation
as Figure 7. `sparse_network_counterfactual_summary.csv` reports a matched
11-site daily-mean MAE of 6.050 µg/m³ against a random-network median of
1.821 µg/m³ (98.87th percentile), and `sparse_network_week_bootstrap_ci.csv`
reports a week-block bootstrap CI of [4.02, 9.00] and a mean bias of +5.956
µg/m³ (CI [3.82, 8.92]). These agree with the manuscript's reported 6.05 /
1.82 / +5.96 µg/m³ to three decimal places — close enough that this is
almost certainly the same computation, not a coincidence.

**What is still open.** Two things do not fully match and are not silently
reconciled:
1. The recovered script (`generating_script_as_supplied.py`) draws 3,000
   unconstrained random networks; the manuscript states 10,000. The point
   estimates match despite this, but the exact run behind the published
   numbers (10,000 draws) has not been located.
2. The manuscript's second randomization reference — 8,029
   geometry-constrained networks, median MAE 2.20 — is not present in this
   archive at all. This half of Section 5.6 remains unrecovered.

See `data/archived/same_sensor_representativeness_v1/README.md` for the
full side-by-side numbers and reasoning.

**Separate, non-matching reconstruction.** `results/verified/same_sensor_representativeness/`
(`src/spatial/build_same_sensor_representativeness.py`) was built *before*
the archive above was found, from
`data/derived/spatial/kgmt_airgradient_pm25_hourly.csv.gz` and the existing
`kgmt_station_geometry_features.csv` matching. It uses only 6 of the 11
KGMT stations (the other 5 had no overlapping AirGradient data in its
window), a different random-alternative construction (2,000 draws,
substituting one station at a time rather than resampling full 11-site
networks), and gets MAE 26.7 µg/m³ (matched) vs. 20.4 µg/m³
(random median) — the same qualitative direction as the manuscript, but
not the same numbers as either the manuscript or the recovered archive
above. It is kept in the repository as a documented, independent check,
not as evidence for the manuscript's reported values — cite the recovered
archive in `data/archived/same_sensor_representativeness_v1/` instead.

## Figure 7 feature-set question: two further one-shot attempts, both unresolved

Beyond the coordinate-only reconstruction already described below, two
further single, non-tuned attempts were made against
`data/archived/spatial_block_cv_107/airgradient_spatial_blocks_107.csv`,
using every extra column present in that recovered cohort file plus
RandomForest/XGBoost with generic (not tuned-to-match) hyperparameters:

| Feature set | Model | MAE_pooled | RMSE_pooled | R2_pooled | RMSE_block_macro |
|---|---|---|---|---|---|
| lon, lat, `median`, one-hot `cluster_id` | XGBoost | 2.078 | 3.270 | 0.847 | 3.456 |
| lon, lat, one-hot `cluster_id` (no `median`) | XGBoost | 4.657 | 5.940 | 0.496 | 5.732 |
| — target (archived `XGB_coordinates`) — | — | **4.135** | **5.600** | **0.552** | **5.045** |

Neither matches. The first (adding `median`) performs far *better* than
the target — `median` is a near-duplicate of the target `pm25` at the
station level, so this is very likely leaking target information rather
than recovering the original feature set, and should not be used. The
second (adding only `cluster_id`) comes closer than lon/lat alone but still
does not reproduce the archived RMSE/R². These two results were recorded
as obtained, without further hyperparameter search or feature trial —
continuing to search combinations until one matches would be exactly the
"tuning against the test set" this repository's scientific safeguards rule
out (see `README.md`). The exact feature set behind the archived
`XGB_coordinates` model remains an open item for the authors.

## Figure 7: recovered archive, plus a reconstruction discrepancy worth noting

**What matches the manuscript.** `data/archived/spatial_block_cv_107/spatial_block_cv_summary.csv`
was recovered on 2026-09-22 from `almaty_review_v4.zip`
(`data/advanced_validation/spatial_block_cv_summary.csv` in that package),
which had not previously been copied into this repository. It reports, for
the same 107-station cohort, IDW/Quadratic/Linear/RF_coordinates/XGB_coordinates
models evaluated on the same 5-fold spatial-block partition:

| model | RMSE_pooled | RMSE_block_macro |
|---|---|---|
| Quadratic | 8.19 | 10.30 |
| IDW | 8.10 | 7.40 |
| Linear | 6.39 | 6.87 |
| RF_coordinates | 6.41 | 5.76 |
| **XGB_coordinates** | **5.60** | **5.04** |

XGB_coordinates has the lowest pooled and block-macro RMSE — this matches
the manuscript's Figure 7 caption. The station cohort file
(`data/archived/spatial_block_cv_107/airgradient_spatial_blocks_107.csv`)
was recovered alongside it, with a richer column set than the minimal
reconstruction described below: `station_id, pm25, median, lat, lon,
station_name, cluster_id, cluster_name, n, spatial_block`.

**What is still missing.** The script that produced these numbers was not
found anywhere in the supplied materials (searched all `.py` files in
`almaty_review_v4.zip` for the strings `XGB_coordinates`/`RF_coordinates`;
only `scripts/03_audit_advanced_validation.py`, which reads the CSV but
does not generate it, references them). So this is preserved archival
evidence — like Figures 4 and 5 — not something regenerable from source in
this repository. In particular, the exact XGBoost/RandomForest
hyperparameters and the exact feature set are unknown: [clarify with
authors] whether `XGB_coordinates` used only `lon, lat`, or also
`cluster_id`/`median`/other columns present in the recovered cohort file.

**Why a from-scratch reconstruction gave a different answer.**
`src/spatial/reproduce_spatial_block_cv.py` (existing deterministic
baselines) plus `src/spatial/add_coordinate_xgboost_baseline.py` and
`src/spatial/tune_coordinate_xgboost_nested_cv.py` were
run against an independently-rebuilt 107-station cohort
(`data/derived/spatial/airgradient_spatial_blocks_107.csv`, built from raw
hourly AirGradient data using a ≥90% coverage threshold, with
`spatial_block` assigned via the same `KMeans(n_clusters=5,
random_state=20260904, n_init=20)` method) using ONLY `lon, lat` as
features. Full output: `results/verified/spatial_block_cv_107/`.

| model | RMSE_pooled | RMSE_block_macro |
|---|---|---|
| TrainingMean | 10.00 | 9.29 |
| XGBoost_coord_only (fixed params) | 9.21 | 8.45 |
| XGBoost_coord_only_tuned (nested-CV) | 9.50 | 8.35 |
| IDW | 8.09 | 7.39 |
| Quadratic | 8.18 | 10.29 |
| **Linear** | **6.38** | **6.86** |

Here Linear wins, not XGBoost, even after a leakage-controlled nested-CV
hyperparameter search (`tune_coordinate_xgboost_nested_cv.py`: per outer
fold, hyperparameters were chosen by inner cross-validation on the
training blocks only, never touching the held-out test block). The most
likely explanation is that the archived `XGB_coordinates` model used
additional features beyond raw `lon, lat` (the recovered cohort file has
several candidates: `cluster_id`, `median`) — not that the manuscript's
figure is wrong, and not that this reconstruction's code is wrong. This is
recorded as an open methodological question for the authors, not resolved
by guessing which extra features were used and tuning until the numbers
match, which would defeat the purpose of an honest reconstruction.
## Guidance for citing these figures

- Figures 3, 4, 5, 6, and 7 are safe to point a reviewer to directly by
  citing their *archived* source data (6 and 7 are archived, like 4 and 5 —
  recovered output; for 6 the generating script is also present, for 4/5/7
  it is not).
- For Figures 1 and 2, either regenerate `src/figures/make_verified_figures.py`
  to match the manuscript's exact plotted quantities, or reword the
  manuscript captions / this table so they are not implied to be the same
  figure.
- For Figure 6, cite `data/archived/same_sensor_representativeness_v1/`
  (matches to 3 decimal places) rather than
  `results/verified/same_sensor_representativeness/` (a separate,
  non-matching reconstruction, kept only as a documented independent
  check). Two open items remain even for the matching archive: the 3,000-
  vs-10,000-draw discrepancy, and the missing geometry-constrained
  reference — worth locating for completeness, but they do not block
  citing the recovered archive's point estimates.
- For Figure 7, the open item is the unknown feature set behind the
  archived `XGB_coordinates` model. Two further one-shot attempts
  (2026-09-22) did not resolve it — see above — worth locating the
  original code for completeness, but it does not block citing the
  recovered archive itself.
